cPanel Deploy Console

Getting it onto your server, and what happens after you do

A walkthrough for putting the deploy console on shared cPanel hosting where the terminal is switched off, plus a look under the hood at how a button click on that page turns into a real composer install or artisan migrate running on the server — without SSH.

Part 1

Getting it onto cPanel

Five steps, all inside the browser — File Manager and a couple of cPanel screens you already use. Nothing here needs a terminal.

  1. Upload and extract the zip

    Open cPanel → File Manager, go into public_html, and upload the zip. Right-click it → Extract.

  2. Rename the folder to something unguessable

    This tool can run shell commands, so its URL is worth protecting like a login page. Don't leave it at an obvious name.

    # instead of public_html/deploy/ # rename to something only you'd guess public_html/deploy-x7f2q9/

  3. Visit the URL and set a password

    First visit shows a one-time setup screen. Use a long, random password — it's hashed and stored locally, never in the code.

  4. Add each project you host on the account

    On the Projects tab, add one entry per app — this is what lets one console manage several sites on the same shared account.

    Absolute Path /home/youruser/myapp PHP CLI Binary php # or a full path from System Check Composer.phar (blank = shared one, downloaded once)

  5. Run your first command

    Switch to the project on the Dashboard and click a quick command, or check the System Check tab first if anything looks uncertain about your host's setup.

⚠ this is a web shell — treat it like one

Anyone who reaches this URL with the password can run commands as your hosting account. That's the whole point of the tool, so:

  • Use a password you haven't reused anywhere else, 12+ random characters.
  • Keep the folder name private — don't link to it, don't commit it anywhere public.
  • Delete the tool (or at least its data/ folder) once you're done deploying for the day.
  • Confirm yourdomain.com/<folder>/data/config.json returns a 403, not the file — that's the .htaccess guard doing its job.
Part 2

What actually happens when you click a button

cPanel disabling the terminal blocks your shell access — it doesn't block PHP's. Shared hosting still lets the PHP process itself start other programs, through functions like proc_open(). This tool is a thin, password-gated web page in front of that one fact: a button click is a form submission that ends, a few steps later, in PHP starting composer or php artisan exactly like a terminal would.

01 · access

Password + CSRF, every request

The password is hashed on disk, never in code. Every action also carries a per-session CSRF token, and five failed logins lock an IP out for 15 minutes.

02 · execution

Falls back through four exec methods

Tries proc_open first, then exec, shell_exec, system — whichever your host hasn't disabled. System Check shows which one won.

03 · environment

HOME and COMPOSER_HOME, set for you

PHP-FPM processes often start with no HOME, which is why Composer errors with "the HOME or COMPOSER_HOME environment variable must be set." Every command gets both, pointed at a folder inside data/.

04 · isolation

Scoped to one project folder

Each command runs with its working directory set to exactly the project you picked — never anywhere else on the account.

05 · composer

No global Composer needed

Most shared hosts don't have composer on the PATH. System Check can download a shared composer.phar once, reused by every project.

06 · record

Every run is logged

Timestamp, IP, command, and exit code go to data/logs/activity.log — protected by the same .htaccess rule as the rest of data/.
